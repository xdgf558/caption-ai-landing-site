# Cat Life Game website integration

The browser game is published as a static sub-application at `/games/cat-life/`. Its runtime was copied from `xdgf558/cat-life-game` at merge commit `0cc839f` and is currently released as website game version `1.20.1`. The Station Cat integration files are `site-integration.js`, `site-integration.css`, `content-manifest.js`, and `commerce.js`; the copied `index.html` and `src/js/main.js` contain the hooks that load them and apply a requested language.

The four indexable product pages live at `/en/apps/cat-life-game/`, `/ja/apps/cat-life-game/`, `/zh-hans/apps/cat-life-game/`, and `/zh-hant/apps/cat-life-game/`. The playable runtime is marked `noindex` and excluded from the sitemap so search results point to a localized product page instead of the application shell.

The guest save key remains `catGameSaveV1`. After sign-in, local progress is stored in an account-specific `catGameSaveV1:member:<accountId>` slot so changing accounts on a shared browser cannot upload another member's progress. The first eligible member may claim the existing guest save once; later accounts load their own local slot, their own cloud save, or a fresh game. The product-page `lang` parameter is a session-only display override and must never replace an existing saved language. Only a language change made inside the game's settings is persisted.

Signed-in Station Cat members also receive a revisioned cloud save through `/api/readers/game-saves/cat-life`. Guests keep playing with the local save and the sign-in link sends them to the locale-matched member center with a safe `returnTo` path back to the game. A member's first local save is uploaded automatically when no cloud save exists. The sync marker records separate local and cloud digests because the restored local game and the compact server payload are intentionally different representations. When both sides have changed since the last successful sync, the game asks which progress to keep instead of choosing by timestamp or silently overwriting either copy. Applying a cloud save first keeps a local recovery copy under `catGameLocalBackupV1:<accountId>`.

Cloud saves are account-scoped, capped at 750,000 UTF-8 bytes, use optimistic revision checks, and retain the five most recent server revisions in `reader_game_save_backups`. The Worker streams and bounds request bodies before parsing instead of buffering an unbounded body. Valid PUT requests require the exact same-site `Origin` header and are limited to 20 writes per member and game in a 60-second fixed window; malformed JSON, unsupported schemas, and oversized saves are rejected before consuming this quota. The client normally waits five seconds after the latest local save before uploading and performs the same size check locally. Device-local custom music data is intentionally removed before upload and restored from the current browser after a cloud save is applied. The API and UI fail closed for cloud writes but fail open for gameplay: a network, session, migration, or rate-limit failure keeps the active local slot intact and the player can continue locally.

The game uses an integer `schemaVersion` independently from the public app version. Schema 0 migrates legacy `player.coins` to `player.gold`; schema 1 migrates the former shared `settings.musicVolume` into `bgmVolume` and `sfxVolume`; schema 2 is current. Migrations run in order on a cloned object before normalization and never mutate the stored source. The Worker repeats these canonical migrations and rejects a schema 2 payload that still carries legacy fields. If an older browser build encounters a future schema, it leaves the original key untouched and switches play to a separate `compat-v<version>` local slot instead of blanking the page or overwriting the newer save.

Members can inspect recovery metadata at `GET /api/readers/game-saves/cat-life/recovery` and restore a retained revision with a same-origin `POST`. A restore requires both the selected backup revision and the current base revision. One D1 batch archives the current save, conditionally installs the selected backup as a new revision, records the action in `reader_game_save_recovery_events`, and trims the backup set. The game also keeps its device-local safety copy before applying the restored cloud payload.

Apply `migrations/0031_reader_game_saves.sql` and then `migrations/0032_reader_game_save_recovery.sql` to the production D1 database before deploying the Worker and game assets. Verify guest play, member return from the login page, first upload, a second-device conflict, both conflict choices, recovery history, and one restore after deployment. To roll back the feature, remove the cloud client hook and API routes while leaving the tables in place; local saves continue to work and the stored cloud data remains available for a later redeploy.

Run `npm test` for Worker/D1 behavior and `npm run test:browser` for the Chromium flow. CI installs Chromium and covers legacy migration, oversized local saves, recovery UI and persistence, and a revision race that must open the conflict chooser.

The runtime uses unversioned file names, so all `/games/cat-life/*` responses require revalidation instead of mixing a fresh HTML shell with cached JavaScript from another snapshot. The same route has a game-specific CSP that permits only same-origin scripts and images, the two Bitcoin data APIs used by the lottery feature, and local/data audio. Keep this policy in place while the game shares the main `wwwstationcat.org` origin. Before connecting member sessions, evaluate moving the runtime to a dedicated game subdomain with an explicit cross-origin API contract.

When updating the embedded game, copy the upstream `index.html` and `src/` tree, then reapply the Station Cat shell hooks and update both `upstreamSourceCommit` in `src/data/products/cat-life-game.ts` and the regression expectations in `scripts/test-cat-life-game-integration.mjs`. This field identifies the imported upstream snapshot; `latestVersion` identifies the Station Cat website release after integration changes. This manual snapshot is acceptable for the first integration, but repeated releases should replace it with a pinned submodule, subtree, or build-time sync step so upstream updates cannot silently discard the website hooks.

The planned Station Points catalog and server-authoritative ownership boundary are defined separately in `docs/cat-life-game-commerce-v1.md`, with a Worker-only machine-readable contract at `server/catalog/cat-life-game-commerce.v1.json`. Never import that seed file into the product page or game client; both must read current prices and ownership from server APIs. Keep all catalog entries non-purchasable until the commerce contract's activation checklist is complete. Every game content release must also update the in-game version history with localized release notes.

Version 1.19.0 ships the first complete content assets and moves client rendering rules into the frozen public `content-manifest.js`. The manifest contains product IDs, entitlement keys, asset paths, supported cats, room options, fixture conditions, and layout coordinates, but it deliberately contains no price, balance, ownership, redeemability, or lifecycle state. Those values continue to come only from the server APIs.

Version 1.19.1 adds a fail-closed commerce rollout gate, account-scoped offline entitlement selection, and immediate visual removal after a server entitlement is revoked. These controls do not change the 1.19.0 content manifest or make either product purchasable by themselves.

Version 1.19.2 moves the Station Points member catalog into its own navigation page and removes the duplicate player-resource summary from the regular gold shop. It also tightens the game-wide card, type, image, control, and spacing scale; mobile shop cards use a compact horizontal layout, while stamina, mood, and hunger use live battery-style meters in the masthead. The commerce API, rollout gate, prices, and entitlement boundary are unchanged.

Version 1.20.0 replaces the previous broadsheet layer with a warm hand-drawn storybook interface based on the delivered Cat Life UI reference. It adds a responsive sticker-card system, segmented live status meters, a stable desktop sidebar, a five-tab mobile bar, action-sensitive cat poses, and a categorized regular shop. All existing save data, game rules, Station Cat member sessions, cloud saves, Station Points entitlements, purchase payloads, and commerce rollout gates remain unchanged.

Version 1.20.1 fixes Cat Town neighbor markers jumping when their hover style replaced the positioning transform, removes a legacy adjacent-row margin that misaligned the three-column player and cat status meters, aligns the recovery action with the language selector without letting the locale note change the primary control row, and restores a compact local Phosphor icon for every work opportunity. Markers remain anchored to their map coordinates and retain only the intended subtle lift feedback; community visits, relationships, and save data are unchanged.

Moonlit Tabby changes only the `cat_001` sprite after the official skin entitlement is present. The Station Room Set exposes four coordinated room options and renders its bench, signal lamp, station clock, and departure board only while the official room entitlement is present. Imported or edited save values fall back to the free room defaults and never render paid fixtures without ownership. An offline entitlement cache may keep an already synchronized cosmetic visible, but it cannot redeem, restore, or create server ownership. See `docs/cat-life-game-content-packs.md` for the asset and renderer contract.

Both initial catalog entries remain `planned` after this client release. Before activating either product, apply migrations `0033`, `0034`, and `0035`, deploy the Worker and static assets together, verify the production catalog and entitlement responses, run a controlled account redemption and correction, and confirm the Admin history. Activation is then an explicit Admin action with the exact product ID; shipping the client alone does not put a product on sale.
