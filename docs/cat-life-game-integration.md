# Cat Life Game website integration

The browser game is published as a static sub-application at `/games/cat-life/`. Its runtime was copied from `xdgf558/cat-life-game` at merge commit `0cc839f` (game version `1.17.0`). The Station Cat integration files are `site-integration.js` and `site-integration.css`; the copied `index.html` and `src/js/main.js` contain the small hooks that load them and apply a requested language.

The four indexable product pages live at `/en/apps/cat-life-game/`, `/ja/apps/cat-life-game/`, `/zh-hans/apps/cat-life-game/`, and `/zh-hant/apps/cat-life-game/`. The playable runtime is marked `noindex` and excluded from the sitemap so search results point to a localized product page instead of the application shell.

The guest save key remains `catGameSaveV1`. After sign-in, local progress is stored in an account-specific `catGameSaveV1:member:<accountId>` slot so changing accounts on a shared browser cannot upload another member's progress. The first eligible member may claim the existing guest save once; later accounts load their own local slot, their own cloud save, or a fresh game. The product-page `lang` parameter is a session-only display override and must never replace an existing saved language. Only a language change made inside the game's settings is persisted.

Signed-in Station Cat members also receive a revisioned cloud save through `/api/readers/game-saves/cat-life`. Guests keep playing with the local save and the sign-in link sends them to the locale-matched member center with a safe `returnTo` path back to the game. A member's first local save is uploaded automatically when no cloud save exists. The sync marker records separate local and cloud digests because the restored local game and the compact server payload are intentionally different representations. When both sides have changed since the last successful sync, the game asks which progress to keep instead of choosing by timestamp or silently overwriting either copy. Applying a cloud save first keeps a local recovery copy under `catGameLocalBackupV1:<accountId>`.

Cloud saves are account-scoped, use optimistic revision checks, and retain the five most recent server revisions in `reader_game_save_backups`. PUT requests require the exact same-site `Origin` header and are limited to 20 writes per member and game in a 60-second fixed window; the client normally waits five seconds after the latest local save before uploading. Device-local custom music data is intentionally removed before upload and restored from the current browser after a cloud save is applied. The API and UI fail closed for cloud writes but fail open for gameplay: a network, session, migration, or rate-limit failure keeps the active local slot intact and the player can continue locally.

Apply `migrations/0031_reader_game_saves.sql` to the production D1 database before deploying the Worker and game assets. Verify guest play, member return from the login page, first upload, a second-device conflict, and both conflict choices after deployment. To roll back the feature, remove the cloud client hook and API route while leaving the tables in place; local saves continue to work and the stored cloud data remains available for a later redeploy.

The runtime uses unversioned file names, so all `/games/cat-life/*` responses require revalidation instead of mixing a fresh HTML shell with cached JavaScript from another snapshot. The same route has a game-specific CSP that permits only same-origin scripts and images, the two Bitcoin data APIs used by the lottery feature, and local/data audio. Keep this policy in place while the game shares the main `wwwstationcat.org` origin. Before connecting member sessions, evaluate moving the runtime to a dedicated game subdomain with an explicit cross-origin API contract.

When updating the embedded game, copy the upstream `index.html` and `src/` tree, then reapply the Station Cat shell hooks and update both `sourceCommit` in `src/data/products/cat-life-game.ts` and the regression expectations in `scripts/test-cat-life-game-integration.mjs`. This manual snapshot is acceptable for the first integration, but repeated releases should replace it with a pinned submodule, subtree, or build-time sync step so upstream updates cannot silently discard the website hooks.
