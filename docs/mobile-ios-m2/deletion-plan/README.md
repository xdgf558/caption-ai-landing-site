# Station Cat 全站账号销户方案（审查草案）

日期：2026-09-16。范围：同一 reader 账号在音乐、小说、会员/积分、游戏中的个人数据及凭据。**本轮交付是数据盘点、保留决策草案、执行设计和内存数据库验证；没有接入真实清理器，没有生产迁移。** `policy-draft.json` 的 approved / executionEnabled 均为 false。

## 现状与证据

从仓库迁移重建了 reader（包含 mobile 扩展）与 music 两套内存 SQLite，共 86 张表，所有表均被显式分类。完整列、外键和迁移哈希见 [schema-inventory.json](schema-inventory.json)，人可读矩阵见 [table-matrix.md](table-matrix.md)。这是代码静态结构审计，不是生产数据库内容或实际迁移版本核对。

当前 `src/mobile/deletion.js` 的 confirm 会原子地冻结账号、撤销网站及原生会话并写 outbox；消费者停在 `attention_required / retention_policy_review`。此行为原样保留，不能解释为已清理数据。常规网站/原生登录检查 active 状态，但后台异步发放与资金回调仍需单独加阻止复活的逻辑。

十项内存数据库测试复现并锁定这些事实：

- `reader_credit_ledger` 随账号 CASCADE 删除；没有其他外键阻拦时，盲删账号会丢失账本。
- `game_purchases` / `game_entitlements` 等使用 RESTRICT，退款复核表使用 NO ACTION，有数据时直接删账号会失败。
- `novel_orders.account_id` 设为 NULL 后，`customer_email` 和 `metadata_json` 仍存在；删订单也不会自动清除 `novel_payment_events.payload_json` 内的邮箱。
- `game_commerce_rate_limits` 有 account_id 却没有账号外键；不能只扫描 FK。
- 云存档、备份与评论可随账号级联删除；两账号的合成数据验证了作用域。
- `mobile_deletions` 没有账号 FK，receipt 可继续查询，但内部仍有 account_id，最终还需最小化。
- 音乐库没有 reader 的服务端收藏/最近播放表；媒体的 owner_track_id / owner_collection_id 是曲目/专辑归属，不能当成会员归属。

## 拟定产品规则

以下是待确认的方案，不以编码代替用户对数据处置的决策。

| 数据或权益 | 拟定处理 | 需确认 / 完成的事项 |
| --- | --- | --- |
| 账号登录身份 | 确认后立即禁止登录与写入，撤销会话、授权码、密码、TOTP 和刷新秘密 | 清理阶段覆盖 old web / native 的所有凭据副本；停用不等于完成销户 |
| 书签、阅读原始事件 | 删除账号关联的个人内容和可识别字段 | reading_events 的 session_id、JSON 与哈希不得仅 account_id=NULL 就称匿名 |
| 游戏云存档与最近备份 | 删除存档、全部恢复备份、恢复事件和账号限流行 | 保留普通公开游戏产品目录；不能删除其他账号的存档 |
| 公开小说评论 | 用户确认匿名保留正文；解除作者关联并最小化个人元数据 | 需迁移现有非空外键并适配查询；正文也可能识别人，不能只换昵称或改变审核状态 |
| 积分余额 / 未结订单 | 不自动退款、不自动扣光、不改历史金额；另建最小资金处理案件 | 默认建议个人资料清理继续、资金案件独立。未确认前不实现账务变更 |
| 已购买小说 / VIP / 游戏装扮 | 账号不再可用，阻止后台重新授予可用权益；最小交易证据隔离保留 | 不等于自动退款；按原规则处理支持请求，不能迁给同邮箱新账号 |
| 订单 / 积分账本 / 拒付退款记录 | 仅保留获批准的对账、争议与审计字段，并限制访问 | 字段白名单、具体期限、适用处理依据、保管位置与责任人未确定；当前不得自动销毁或无限期默认保留 |
| 删除回执 / 任务 | 保留独立只读最小结果，支持无账号查询 | 当前 receipt 查询 14 天；任务审计保留期及到期支持流程需另定，不把 14 天当财务期限 |
| 音乐本机收藏/最近播放 | 网站本来就不随账号同步；提供本设备显式清理，不能承诺远程擦掉其他设备 | iOS 当前 Mock 收藏为进程内；M5 云同步若加入，必须先更新本方案 |
| 音乐匿名统计 | 不臆造与账号的关联，不扫除全站统计 | 现有原始事件 30 天、无会话每日汇总 365 天继续沿原规则；会员归因当前不采集 |
| 本地游戏存档、下载文件、用户导出的 JSON | 告知不受服务端直接控制 | 不把删除服务器记录称为删除所有副本；用户可手动清理或先导出 |

积分当前网页规定：未使用积分可联系支持申请退款，按适用法律与服务商政策处理；有效账号内的已购积分通常无到期日。销户方案不得悄悄改为“自动作废余额”或“自动退款”。这里没有给出法定财务保留年限；`financialRetentionDays=null` 是明确的启用阻断项，待运营主体、服务地区和政策确认。

## 最小身份与审计保留设计

建议把“停止账号、删除个人资料”与“按批准期限保留最小财务证据”分开。现有大量账务外键不能直接脱离 reader_accounts，因此可先保留禁止认证的技术主体行，去除邮箱、标准化邮箱、显示名等登录身份，以不可登录的随机内部占位替代唯一键。此方案需要显式迁移和状态语义；**本轮不修改现有 account 表，也不把设置 status 当作清理完成。**

保留 account ID 与交易引用仍是可关联的去标识数据，不是不可逆匿名化。需要独立访问控制、审计、到期清理与对应的删除任务依据。不要将所有历史交易搬到另一个无期限“归档 JSON”里充数，也不要改变不可变积分金额和已有退款事件幂等键。保留依据结束且所有 RESTRICT/NO ACTION 依赖清理后，才可物理移除该技术主体。

同邮箱未来重新注册必须得到新账号 ID，不恢复旧权限/余额/装扮。旧支付回调必须绑定原订单、原账号主体与 provider event ID；禁止凭邮箱把旧支付发给新账号。此项依赖后端发放路径在同事务检查销户屏障。

## 执行状态机与事务边界（待实现）

1. **accepted / queued**：沿用现有 confirm 原子事务。写入不可变 deletionRequestId、scopeVersion、policyVersion、确认时间与独立 receipt。准备阶段不撤销账号；只在显式确认后停用。
2. **processing / inventory**：以精确 account ID 和确认前身份快照盘点关联，建立字段级计划摘要、保留决策引用及有限重试次数。原始邮箱或敏感快照必须加密、短期保存，不能进入日志或 receipt 返回体。
3. **processing / credentials**：撤销并清理 web 登录 token/session、密码/TOTP、mobile codes/sessions/refresh tokens/refresh 密文。先子表后父表；不清掉删除 receipt。保护同库批次原子性。
4. **processing / private_data**：按允许表和列清理书签、个人阅读事件、存档/所有备份、评论（按批准选择）、账号限流。每个 stage 有唯一 job/stage/policyVersion 键，重复执行得到相同结果。不得拼接用户传入表名或 SQL。
5. **processing / financial_review**：余额、未结支付、退款与争议产生独立资金案件；个人数据部分可继续，但任何保留字段必须有批准依据。保留白名单并最小化身份与原始 payload；不自动出账，不触发真实退款。
6. **processing / external_cleanup**：按各存储实际所有权逐项处理 R2、支持记录、通知和备份恢复屏障。没有已核验的对象键或主体关系就转 attention_required，不能全桶删除或按邮箱全文搜删。
7. **processing / verification**：用拒绝名单验证身份秘密、普通个人资料、旧会话和可用权限均不能残留；保留名单验证每条存续数据有用途、字段范围、到期点。消费失败、字段未知或外部系统不可达均不能标 completed。
8. **completed**：仅当全部必要清理完成、保留政策已批准并与用户说明一致时写入完成标记。最小回执只呈现状态、阶段、时间；不回传原邮箱、账号资料、订单或余额。若仅部分清理，保持 processing / attention_required。

队列只是唤醒机制，持久 D1 outbox 才是任务依据。跨 D1 / R2 / 支付服务不能假设单事务；外部阶段必须先记录幂等意图，执行后记录证明。任务 lease 过期可由新消费者重试，不发起第二次用户确认。外部成功后回写失败也应以相同 stage ID 核对结果，而非重复破坏性动作。现有 outbox 没有这些完整执行字段，需在后续隔离迁移实现；当前不改成假完整消费者。

## 必须先解决的软关联与写入竞态

| 入口 / 存储 | 当前可见风险 | 实施要求 |
| --- | --- | --- |
| `applyCreditTopupFromOrder`、`grantNovelEntitlementFromOrder`、管理员 grant | 不能仅依赖 session 已撤销；这些后台路径可能更新记录 | 资金事件仍去重记账，但禁止复活可用权限或向 deleted 主体补回个人资料；同事务检查状态/删除版本，不只事前 SELECT |
| `novel_orders.customer_email`、付款事件 payload、metadata/note | 置空 FK 不会删除这些字段；provider payload 可能嵌套个人信息 | 按事件类型字段白名单重建最小审计记录，逐项处理非法/未知 JSON，失败转人工，不静默跳过 |
| waitlist、product_feedback、支持邮件 | 未用账号 FK；邮箱并不能证明所有记录同属该主体 | 验证所有权、时间范围和目的后分类清理/退出通知；对同邮箱后来新注册者的记录不得追删 |

| CONTENT_BUCKET、DOWNLOADS_BUCKET、MUSIC_BUCKET | 当前主要是站点内容、软件或发布者音频封面 | 普通会员销户不删除全站作品与发行文件。只有独立证实是该主体的私人对象才纳入清理 |
| D1 平台备份 / 导出 / 日志 | 仓库看不到实际恢复策略与保留配置 | 上线前核验实际周期；恢复必须重放删除屏障和已完成任务，不能把旧账号/邮箱/凭据重新激活 |
| Apple / Creem / 其他支付提供方 | 本站删除不等于自动取消订阅或删除平台侧记录 | UI 清楚区分服务账号删除与平台续费管理；不依赖用户先取消才接受删除。StoreKit 当前尚未接入 |

## 执行前决策与审查清单

2026-09-20 用户确认：公开评论匿名保留；有余额/争议时继续清理个人资料，余额及争议另立处理记录，不自动退款或清零。此确认只覆盖两项业务选择，不代表整份执行政策获批。具体财务保留期、最小字段、账务处置、支持身份核验、平台备份恢复规则仍需独立确认；整体 `approved` / `executionEnabled` 继续为 false。

当前 `reader_comments.account_id` 为 NOT NULL，外键为 CASCADE，直接删除账号会连同评论删除；仅将账号显示名改为“已注销”也仍保留作者关联。因此需要独立评审可空作者迁移、匿名评论读取（包括原有 INNER JOIN）、写入规则和元数据最小化。保持正文与原有审核状态，不将待审核/隐藏评论重新发布；正文内可能有作者主动写入的个人信息，需要配套处理渠道，不能声称绝对匿名。该迁移及执行器本轮尚未实现。

个人资料清理与财务案件解耦后，未完成的必要保留/外部处理仍阻止整个任务进入 completed。没有这些规则，保持 `attention_required`；不是以等待为由声称销户完成。

下一份实现 PR 应包含：隔离版本化迁移、只读 dry-run 计划、各阶段幂等消费者与 lease、出站任务白名单、余额案件分离、支付回调防复活、最小化白名单与完成检查器、管理员审计和告警；仍只在合成数据隔离环境执行。进入真实环境前再核验已部署 schema / 数据存储与本盘点是否一致。

验收必须覆盖：A/B 账号隔离；零余额/正余额/负余额；未结/成功/退款/拒付/重复或迟到支付事件；游戏 RESTRICT 与退款复核依赖；同邮箱重新注册；stage 中断/重复/乱序/lease 接管；平台故障；未知 JSON 字段；存档备份恢复；receipt 丢失/超期/跨任务访问；完成后继续尝试 web/native 登录和后台发放。未完成的外部清理必须保留可观察状态，不能成为被吞掉的“成功”。

## 本轮复现

```sh
python3 scripts/audit-account-deletion.py
python3 scripts/test-account-deletion-audit.py
```

脚本只使用 `sqlite3.connect(':memory:')`，没有数据库文件参数、网络或删除执行入口。新增/变化的迁移会使 snapshot 检查失败，必须重新审查分类后生成。需要更新时用 `--write`，但这只写文档，不批准政策、不改变运行时。
