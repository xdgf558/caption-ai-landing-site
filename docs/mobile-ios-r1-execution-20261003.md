## 本批实际执行的内容

### 独立删除台账和旧快照恢复

CONTROL 使用与 reader 分离的 D1；另有独立保护的 anchor，固定台账身份、namespace、递增水位和哈希链摘要。先登记确认后的删除墓碑，再执行 reader 个人清理。不能从旧 CONTROL 数据库重新生成丢失的 anchor；空台账初始化、CONTROL 提交成功但 anchor 写入失败均有同一状态重试路径。墓碑不能被更新/删除；上限 10,000 条，达到上限在写入前明确阻断，不遗忘旧墓碑。

旧 reader 恢复首先处于隔离状态，冻结写入并逐项重放当前 CONTROL 中的删除任务。按最多 25 条一批完成可续跑验证，在独立 CONTROL 封存结果后再发放 30 秒的读取准入证明；读取前后有界核对封存结果、数据修订号及当前水位，等待期间新增墓碑则丢弃读结果。缺失/错误 namespace、回退的 CONTROL、过期证明、半途重启或未知数据库结构均拒绝准入。

这是受控恢复演示。数据库触发器不能封锁任意原始 SELECT；调用方必须经过准入包装器，实际服务还需具备可信 registry、独立保护的 anchor 和并发准入机制。本批只接受已审核的基线 reader 快照及可选 completion schema；包含本批 financial/external 扩展的快照需另行定义恢复契约，目前明确拒绝。详见 [控制面边界](../scripts/isolated-lifecycle/CONTROL-RESTORE.md)。没有操作 Cloudflare 平台备份或生产数据库。

### 财务个人字段最小化和到期清除

新增 `synthetic-erasure-v1` 执行 profile，政策版本、完整规范化政策、摘要、确认时间和期限固定保存。14 张已审核财务表按精确账号/订单/账本关联执行，每次单表至多 200 行；被批准保留的金额、账务引用和余额不改，个人 review 字段按明确规则置空或清为最小 JSON。未知列、未知 JSON、矛盾关联、缺失屏障或超过既有 200 行 JSON 审核边界均阻断。

写入许可证仅在同一 D1 事务内出现，限定工作者、租约版本、表和行，失败整体回滚。最小化后进入 `retained`。期限到达后，必须另有与政策和确认时间一致的合成案件回执，并核实真实余额为零，才能按子表到父表顺序清除到期财务行。非零余额与未解决案件保持阻断；执行器不自动清零、退款或恢复权益。删除任务、独立墓碑和技术主体不随财务行一起删掉。

冻结账号以及已清除父记录的迟到 INSERT / UPDATE / UPSERT 都有数据库写屏障。无法证明活跃归属的 NULL 父关联、孤立 provider 引用和跨账号改写在此隔离 profile 中拒绝。历史上已经存在、且没有可证明归属的孤立记录仍须另外盘点，不能凭邮箱或 JSON 猜测主体。该严格规则不是直接给真实支付回调套用的生产规则。

### 外部任务、重试和独立结果核查

四类 `soft_links / admin_audit / providers / backups` 使用第三个独立合成服务 D1。每个资源有固定账号归属、服务 adapter、store ID、任务 ID 和幂等 operation ID；保存完整清单后禁止改写。清单必须与受信 registry 中所有 store 的该账号资源盘点一致，不能挑选四个示例资源就宣布完成。

执行会实际删除 fixture 中的内容，并在独立服务库保存不可变结果和账号屏障，阻止换一个 resource ref 重建资料。执行后重新读取结果及残留；工作者返回成功、单独修改本地状态或伪造摘要都不足以完成。失败只记录固定错误码，以相同 operation ID 持久重试；清理已成功但本地回执丢失，重启后核查并恢复，不扩大资源范围。

执行前和提交前均核对租约，并将异步预检耗时计入截止时间。不同数据库之间没有原子事务；外部效果靠不可变范围和幂等结果抵御重复执行，reader 回执只在独立结果核查后更新。本 fixture 的 store 对应单个 reader namespace，不能未经适配用于多个账号编号重叠的 reader。

这不是邮件、支付提供方、日志平台或云备份的真实适配器。实际服务的资源发现、授权、保留限制和删除证明仍须逐个接入验证。合成 fixture 的 `approved:true` 政策仅用于测试，不构成经营政策批准。

### 完成编排

`completeSyntheticExecution` 要求当前独立 CONTROL 中存在同一确认请求的墓碑、财务执行确实达到 `retained`、政策一致、所有外部资源执行和重新读取通过。然后生成内部审查引用，并在 reader 最终事务再次检查财务字段、关联、TOTP 残留、政策期限、证明时效和租约，提交原有 `completed` 回执。

任何前提失败仍保持未完成。最终提交前中断可在租约到期后继续；完成后重试不改确认时间、回执或完成时间。这一执行协调器的重试窗口限于财务仍处于有效保留阶段；财务到期清除后的历史状态查询仍通过原回执通道，不能重新运行协调器代替查询。

## PR #183 复审修复：恢复准入不再重复全量扫描

首轮准入会串行重查全部墓碑和个人残留，1,000 条可能在完成前耗尽 30 秒证明。现在把重查移到可持久续跑的就绪验证：固定每批 25 条，独立 CONTROL 保存 cursor、链摘要、CAS version 及绑定的 reader 数据/工作流修订号。全部完成并封存后才签发短期证明；证明期限仍为 30 秒。之后准入只核对固定元数据和受保护水位，不再随墓碑数量线性增加查询。

reader 受控表的 INSERT / UPDATE / DELETE 同事务推进数据修订。验证途中变动必须从头重验，旧证明不能因数据改回而恢复有效；读取返回前再次核验。reader ready 与 CONTROL seal 之间中断继续拒绝准入，持久重启可完成封存。控制面依然是可信输入：绕过 guard 的特权 SQL 需要完整审计和重新验证，跨库检查与读取仍需生产级并发准入机制。
